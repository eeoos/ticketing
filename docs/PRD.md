# Ticketing PRD — 1차 범위(MVP)

## 목표
사용자가 공연을 고르고 좌석맵에서 좌석 하나를 5분 동안 잡은 뒤, 모의 결제(결제 요청 → 결제사 콜백)로 예매를 확정할 수 있는 **백엔드 API**를 만든다.

## 범위
| 포함 | 제외 |
|---|---|
| 공연 목록 조회 | 화면(프론트엔드) |
| 공연별 좌석맵 조회 | 실제 로그인·회원가입 |
| 좌석 하나 홀드(5분) | 실제 결제 연동, 환불·취소 |
| 모의 결제: 결제 요청(PENDING) + 결제사 콜백(성공·실패) | 공연·좌석 등록용 관리자 기능(시드 데이터로 대신) |
| 결제 요청 멱등성(`Idempotency-Key`) | 여러 좌석 한 번에 잡기 |
| 만료 후 성공한 결제의 "환불 필요" 기록 | **좌석 가격·등급**(이번 범위에서 제외, 결제 금액 개념 없음) |
| | 실제 환불 연동, 사용자 취소, 홀드 직접 해제·연장 |

## 사용자 식별
- 로그인 대신 요청 헤더 `X-User-Id`로 사용자를 식별한다(모의 사용자).
- 상태를 바꾸는 요청(홀드, 결제 요청, 예매 조회)은 `X-User-Id`가 반드시 있어야 하고, 없으면 거절한다.
- 공연 목록은 `X-User-Id` 없이도 된다. **좌석맵은 9장부터 `X-User-Id`와 입장권이 필요하다**(아래 '가상 대기열').

## 좌석 상태
```
AVAILABLE ──홀드──▶ HELD ──결제 성공 콜백(홀드 유효)──▶ SOLD
    ▲                 │
    └───5분 경과(만료)──┘
```
- 홀드는 잡은 시각부터 **5분** 유효하다. `현재 시각 ≥ 만료 시각`이면 만료된 것으로 본다.
- 잡을 수 있는 좌석: `AVAILABLE`, 또는 **만료된** `HELD`.
- 잡을 수 없는 좌석: 만료되지 않은 `HELD`(본인 것 포함), `SOLD`. `SOLD`는 어떤 경우에도 다시 잡을 수 없다.
- 만료된 `HELD`는 조회 시 `AVAILABLE`로 보인다.
- 같은 좌석을 동시에 잡으려 하면 **정확히 한 요청만** 성공한다.
- 결제 요청은 **홀드한 본인**이 **만료 전에** 할 때만 받아들인다. 좌석은 결제 **성공 콜백이 홀드 유효 시간 안에** 도착해야 `SOLD`가 된다.
- 모든 만료 판단은 서버 시각(`get_now()`)으로 한다. 클라이언트나 콜백이 보낸 시각은 쓰지 않는다.

## 홀드 정책 (6장 결정)
- **연장 없음**: 본인이 홀드한 좌석을 만료 전에 다시 홀드하면 409 `SEAT_HELD`로 거절하고 만료 시각은 그대로 둔다. 결제 요청도 홀드를 연장하지 않는다.
- **직접 해제 없음**: 홀드는 만료로만 풀린다. 결제 실패도 홀드를 풀지 않는다(만료 전이면 같은 홀드로 다시 결제할 수 있다).
- 만료 뒤에는 누구든(본인 포함) 새로 홀드할 수 있고, 새 홀드는 새 `holdId`를 받는다.

## 모의 결제 (6장 결정)
결제는 두 단계다. 계약은 `docs/openapi.yaml`, 상태 전이는 `docs/backend-interface.md`.
1. **결제 요청** `POST /bookings` (`Idempotency-Key` 필수) → 예매를 `PENDING`으로 만들고 `paymentId`를 돌려준다. 예매는 요청 시점의 홀드(`holdId`)에 묶인다.
2. **결제사 콜백** `POST /payments/callback` (모의 결제사가 서명해서 보냄) → `SUCCEEDED`면 그 홀드가 아직 유효할 때만 `CONFIRMED` + 좌석 `SOLD`, 아니면 `REFUND_REQUIRED`(좌석은 팔지 않음). `FAILED`면 예매 `FAILED`, 좌석은 그대로.
- 성공·실패는 콜백의 `result`로 흉내 낸다.
- 같은 사용자·같은 키·같은 요청은 최초 응답을 재현하고, 같은 키로 다른 요청을 보내면 409 `IDEMPOTENCY_KEY_MISMATCH`.
- 이미 확정한 본인 예매가 있는 좌석에 **새 키로** 다시 요청하면 그 예매를 200으로 돌려준다(키 재요청 규칙이 먼저).
- 같은 콜백이 여러 번 와도 한 번만 반영한다. 먼저 도착한 최종 결과가 이긴다. 단 `FAILED` 뒤에 `SUCCEEDED`가 오면 돈이 빠져나간 것이므로 `REFUND_REQUIRED`로 바꾼다.
- 결제 실패 뒤 재시도: 홀드가 유효하면 **새 키로** 다시 결제 요청할 수 있다. 홀드당 진행 중(`PENDING`) 결제는 하나뿐이다.
- 좌석당 확정 예매는 하나다. 기존 `bookings.seat_id` UNIQUE는 실패·환불 필요 기록과 재시도를 담을 수 없어서 "확정 예매만 좌석당 하나"인 조건부 UNIQUE로 바꾼다.
- 실제 환불은 하지 않는다. `REFUND_REQUIRED` 기록만 남긴다.

## 가상 대기열 (9장 결정)
티켓 오픈 때 몰리는 사람을 공연별 대기열에 세우고, 차례가 된 사람만 좌석을 보고 잡게 한다. 상세는 `docs/queue.md`.
- **번호표**: `POST /shows/{showId}/queue`. 같은 사용자는 다시 불러도(두 탭이어도) 같은 번호. 번호는 겹치거나 빠지지 않는다.
- **전광판**: 1초마다 최대 200명씩 올라간다(4장 계산 시트의 입장 속도 [가정]). 발급된 번호를 넘지 않는다.
- **내 순서**: `GET /shows/{showId}/queue/me` — 내 번호, 전광판, 앞에 남은 사람 수, 다시 물어볼 초(`Retry-After`, 1~5초).
- **입장권**: 차례가 된 뒤 처음 조회할 때 2분짜리 입장권을 받는다. 헤더 `X-Queue-Ticket`으로 보낸다. 사용자·공연에 묶이고, 다시 조회해도 늘어나지 않는다.
- **입장권이 필요한 요청**: 좌석맵 조회, 홀드. 결제 요청·콜백·예매 조회·공연 목록은 필요 없다(홀드를 잡은 뒤 결제는 홀드가 지킨다).
- **거절**: 입장권 없음·남의 것·다른 공연·만료 → 403(`QUEUE_TICKET_REQUIRED`/`INVALID`/`EXPIRED`).
- **만료 후**: 그 번호는 끝난다. 다시 줄 서면 맨 뒤 새 번호.
- **Redis 장애**: 좌석 캐시·홀드 관문은 DB로 우회하지만, 대기열과 입장권 검증은 우회하지 않고 503 `QUEUE_UNAVAILABLE`(입장시키지 않음).

## 이후 단계: API 계약과 화면
- 엔드포인트 경로, 요청·응답 형식, 오류 코드는 이 문서가 아니라 별도 **API 계약 파일**(`docs/openapi.yaml`)에서 정한다.

## 열린 질문
- 한 사용자가 동시에 여러 좌석을 홀드할 수 있는가? (MVP 가정: 제한 없음, 한 요청에 한 좌석)
- ~~본인이 홀드를 직접 풀거나 연장하는 기능이 필요한가?~~ → 6장 결정: 없음(위 홀드 정책).
- ~~모의 결제 실패를 흉내 낼 방법이 필요한가?~~ → 6장 결정: 콜백 `result: FAILED`.
- 좌석 가격·등급이 언제 범위에 들어오는가? (6장에서도 제외)
- `PENDING`인 채 콜백이 오지 않는 결제를 언제 정리할 것인가? (6장: 정리하지 않음. 홀드가 만료되면 그 결제로는 좌석을 팔 수 없다)
