# Ticketing PRD — 1차 범위(MVP)

## 목표
사용자가 공연을 고르고 좌석맵에서 좌석 하나를 5분 동안 잡은 뒤, 모의 결제로 예매를 확정할 수 있는 **백엔드 API**를 만든다.

## 범위
| 포함 | 제외 |
|---|---|
| 공연 목록 조회 | 화면(프론트엔드) |
| 공연별 좌석맵 조회 | 실제 로그인·회원가입 |
| 좌석 하나 홀드(5분) | 실제 결제 연동, 환불·취소 |
| 모의 결제로 예매 확정 | 공연·좌석 등록용 관리자 기능(시드 데이터로 대신) |
| | 여러 좌석 한 번에 잡기, 좌석 등급·가격 |

## 사용자 식별
- 로그인 대신 요청 헤더 `X-User-Id`로 사용자를 식별한다(모의 사용자).
- 상태를 바꾸는 요청(홀드, 예매 확정)은 `X-User-Id`가 반드시 있어야 하고, 없으면 거절한다.
- 조회 요청(공연 목록, 좌석맵)은 `X-User-Id` 없이도 된다.

## 좌석 상태
```
AVAILABLE ──홀드──▶ HELD ──모의 결제──▶ SOLD
    ▲                 │
    └───5분 경과(만료)──┘
```
- 홀드는 잡은 시각부터 **5분** 유효하다. `현재 시각 ≥ 만료 시각`이면 만료된 것으로 본다.
- 잡을 수 있는 좌석: `AVAILABLE`, 또는 **만료된** `HELD`.
- 잡을 수 없는 좌석: 만료되지 않은 `HELD`(본인 것 포함), `SOLD`. `SOLD`는 어떤 경우에도 다시 잡을 수 없다.
- 만료된 `HELD`는 조회 시 `AVAILABLE`로 보인다.
- 같은 좌석을 동시에 잡으려 하면 **정확히 한 요청만** 성공한다.
- 예매 확정은 **홀드한 본인**이 **만료 전에** 요청할 때만 성공하고, 좌석은 `SOLD`가 된다.

## 모의 결제
- 실제 결제 대신 확정 요청 자체를 결제 성공으로 처리한다.
- 결제 실패 시나리오는 이번 범위에 없다(열린 질문 참고).

## 이후 단계: API 계약과 화면
- 엔드포인트 경로, 요청·응답 형식, 오류 코드는 이 문서가 아니라 별도 **API 계약 파일**에서 정한다(아직 작성 전).
- 테스트(test)와 구현(server)은 그 계약 파일을 공통 기준으로 쓴다.
- 화면은 나중에 계약 파일에서 타입을 생성해 붙인다.

## MVP 완료 조건
- US-01~US-04의 인수 조건이 모두 자동 테스트로 검증되고 `uv run pytest`가 통과한다.
- 테스트는 구현 전에 작성되어 실패(RED)를 확인했고, 구현 뒤 `scripts/verify_tests.py check`로 테스트가 바뀌지 않았음을 확인했다.

## 열린 질문
- 한 사용자가 동시에 여러 좌석을 홀드할 수 있는가? (MVP 가정: 제한 없음, 한 요청에 한 좌석)
- 본인이 홀드를 직접 풀거나 연장하는 기능이 필요한가? (MVP 가정: 없음)
- 모의 결제 실패를 흉내 낼 방법이 필요한가?
- 좌석 가격·등급이 언제 범위에 들어오는가?
